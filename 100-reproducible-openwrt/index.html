100% Reproducible OpenWrt

19 Oct, 2026

This one has been cooking for a long time.

tl;dr: OpenWrt (SNAPSHOT) is now 100% reproducible.

I planned a blog post like this back in 2019 when I first worked on the reproducibility of OpenWrt. The work was initially fueled by h01ger, who kindly invited me to the Reproducible Builds Summit 2019 in Marrakesh. Discussions at the conference motivated me to look into rebuilding firmware rather than building twice in different environments. Previous OpenWrt CI tests would build the same OpenWrt commit twice on two hosts with different times, different build paths, different GCC versions etc., whereas I wanted to check if I could fully recreate the officially published OpenWrt firmware images, therefore “re-building”. In other words, it’s a verification build to prove that whatever was published is really based on the source. While sources for this claim are missing, kpcyrd and I think the term rebuilder was coined at that conference.

openwrt-rebuilder

So it needed a rebuilder for OpenWrt, which became small software that consumes the OpenWrt buildinfo files. They contain the version (version.buildinfo), the build configuration (config.buildinfo) and the package feeds with their respective Git commit (feeds.buildinfo). When running, all files are put in place and parsed, and the official OpenWrt repository is cloned and built.

Initial versions of openwrt-rebuilder compared created artifacts on its own, ran diffoscope and were triggered via GitHub CI. Instead of doing the tracking via CI scripts, the tool was rewritten to be run by rebuilderd. rebuilderd parses upstream, finds new versions and offers a queue for attached workers. The integration bits are still pending, however I’m optimistic about getting this upstream eventually.

Making sense of diffs

Diffoscope is an excellent tool. You hand it two files and it tells you what actually makes them different. A long list of archive formats and binary decoders is supported, so the output is as human readable as possible.

In cases where diffoscope doesn’t know how to proceed, it shows a hexdump. While various AIs are surprisingly good at understanding hex dumps and figuring out what causes reproducibility issues, I’m not. As a consequence, I added APKv3 (not the Android stuff) support to diffoscope, neatly printing issues. Once APK was supported, I struggled with further hexdumps and therefore added further patches. Making sense of results

The patched rebuilderd did a great job at fetching and checking firmwares, however it lacked a convenient way to inspect the results. Inspired by Reproducible Archlinux, I asked an AI to create an OpenWrt page with the old design. The result was this reproducible wireless freedom page and with further inspiration from Debian’s stats, the gamification to reach 100% reproducibility got started.

The OpenWrt frontend is entirely AI generated, pull requests for a better UI/UX are very welcome.

The image below shows the current UI. If a firmware or package isn’t reproducible, a diffoscope link is offered. For all successful rebuilds, an attest is offered, a cryptographically signed document, more on that later.

Lastly, the UI invites you to rebuild the target locally. This can be helpful in case diffoscope couldn’t fully unpack the image and you want to manually investigate. To save space, artifacts aren’t kept on the server itself.

Keeping 100%

The page is nice and 100% feels good, however it’s unclear how to keep it that way. I’m thinking of an automated system to create issues or notify interested developers directly. It’s always a continuous effort, OpenWrt keeps on adding more devices and so more corner cases may introduce unreproducible quirks.

Furthermore, I want to upstream my patches to rebuilderd and diffoscope. Only that way are the next steps really possible.

Independent Rebuilders

When I started with rebuilders, I envisioned that multiple entities, private or institutional, would spin up their own rebuilders and track OpenWrt reproducibility. From one of my other projects, the OpenWrt sysupgrade server, I learned that people do want to help and host those things on their own, but don’t have infinite time to figure out why their local setup doesn’t work. Before working on yet another tool around OpenWrt, I’ll try to make the rebuilder easy to deploy.

Once more people run a rebuilder and generate attests (cryptographic signatures for successful rebuilds based on in-toto), the logs could automatically be stored and warnings triggered, if upstream doesn’t match. This supply chain security of OpenWrt is a bigger undertaking, however I’m looking forward to working on that more in the future.
